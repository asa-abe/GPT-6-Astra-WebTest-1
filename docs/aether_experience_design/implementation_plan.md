## 1. 提案の核

**「技術を説明するのではなく、技術が形になる瞬間を体験させる。」**

架空の先端技術スタジオ「AETHER」を題材に、精密な立体構造が閲覧者の操作に反応し、提供価値・技術・制作例・相談へつながる**1ページ完結のLP**を制作する。目的は、短い閲覧時間で技術力と提供価値を伝え、相談行動につなげること。

単に3Dモデルを置いたページにはしない。ヒーローの「完成形」が技術紹介で「仕組み」に分解され、制作例で「成果」と結び付く。3Dを主役にするのは冒頭に限定し、その後は読みやすい情報とCTAへつなぐ。

最高峰を目指す対象は、使用技術の新しさだけではない。アートディレクション、描画品質、反応の気持ちよさ、読みやすさ、配信速度、継続運用を一体で設計する。**ページ数と運用機能は減らし、体験の密度は落とさない。**

### 1.2 今回つくらないもの

記事一覧、実績詳細ページ、検索・絞り込み、会員機能、CMS、データベース、独立した技術デモページ、独自の問い合わせフォームは作らない。ページ遷移用ルーターやView Transitionsも不要とする。今後必要になった時点で別途設計し、今回の公開条件や見積もりには含めない。

### 1.3 成功の定義

- 最初の画面で「何を提供する組織か」と「次に何をすればよいか」が分かる。
- 2〜3分程度の読み進めで、提供価値・制作例・進め方・相談方法を把握できる。読む速さは利用者に委ねる。
- 3Dなしでも同じ内容に到達でき、相談のために演出の完了を待たない。
- 文言・画像・制作例の差し替えで、レイアウトや3Dコードを編集しない。
- 第7章の性能予算と第12章の公開条件を満たす。

主な計測対象は相談CTAのクリック、相談セクションへの到達、メールリンクのクリック。メールの送信完了・商談成立はLPからは観測できないため、クリックを「問い合わせ完了」として報告しない。

## 2. アートディレクション

### 2.1 世界観: Living Architecture

モチーフは、知性を持つように変形する精密な構造体「Aether Core」。暗い空間、温かい白の文字、繊細なグリッド、少量の発光色を組み合わせる。宇宙・サイバーパンクの記号を増やすのではなく、建築模型や科学機器のような説得力を狙う。

| 要素 | 指針 |
| --- | --- |
| 背景 | `#080B10`。背景全面の動画ではなく、静かな暗部を維持する |
| サーフェス | `#111722`。境界線と濃度差でカード・操作領域を示す |
| 本文 | `#F2F0E8`。補助テキスト候補は`#A8B2C1` |
| 主アクセント | `#9EF0D0`。操作、接続線、選択状態に絞る |
| 副アクセント | `#FFAA76`。要点や観測マーカーに少量使用する |
| 文字 | 英数字はGeist Variable 5.3.0のLatin woff2を自前配信、日本語はOSのシステムフォント |
| レイアウト | PCは12列、タブレットは8列、モバイルは4列。最大コンテンツ幅1,440px |
| 余白 | 8px系統を基本に、セクション間はPC 96〜144px、モバイル56〜80px。LPを間延びさせない |
| 角・線 | 小さな角丸、1px境界線。大きなガラスカードの多用は避ける |

色は候補値。実際の背景、透明度、ホバー、フォーカスを含む組み合わせごとにコントラストを検証する。通常文字4.5:1以上、大きな文字と必要なUI境界3:1以上を公開条件とする。

### 2.2 ファーストビュー

PCでは左側約45%をコピー、右側約55%を構造体に配分する。スクロール前からサイトの目的とCTAが見える。見出しは可変サイズとし、広い画面で72〜112px、モバイルで40〜56pxを目安に実文で調整する。

> **複雑を、美しい体験へ。**  
> リアルタイム3D、インタラクション、デジタルプロダクトを、一つの体験に。  
> 主CTA: プロジェクトを相談する → `#contact`  
> 副CTA: 制作例を見る → `#work`

コピーは仮案であり、実際に提供できるサービスに合わせて承認する。「業界初」「世界最高」や成果数値など、根拠のない実績表現は掲載しない。

### 2.3 音・カーソル・装飾

自動再生音、強制イントロ、独自カーソルによる標準カーソルの置換、画面全体の常時ノイズは採用しない。細いガイド線、章番号、短い状態表示を装飾として使い、専門性を表現する。装飾用の数値を実測値と誤認させない。

## 3. 1ページの構成とコンバージョン

### 3.1 ページ内の情報設計

公開HTMLは`/`のみ。以下のフラグメントはすべて同じHTML内の見出し・領域を指す。制作例の説明やFAQの回答も初期HTMLに含め、別ページやダイアログへ分割しない。

| 順番 | アンカー | 内容 | 役割・表現 |
| --- | --- | --- | --- |
| 1 | `#hero` | 提供価値、補足コピー、主・副CTA | 3D Coreと一目で伝わる見出し。主CTAは`#contact` |
| 2 | `#technology` | 「表現・体験・品質」の3つの強み | Coreの分解と説明を対応させ、技術を利用者の価値へ翻訳 |
| 3 | `#work` | 制作例2〜3件 | 課題・アプローチ・成果・担当範囲を同じページで読める |
| 4 | `#process` | 相談→試作→制作→改善の4工程 | 協働する姿を想像できる説明と、短い運営者紹介 |
| 5 | `#faq` | 相談前によくある質問3〜4件 | 費用の決まり方、期間、原稿・素材、公開後の修正など |
| 6 | `#contact` | 相談の案内、メールリンク、連絡先 | 「構想段階から相談できます」等の承認済みコピー |
| 補足 | `#privacy` | 個人情報の取り扱い、運営者情報 | フッターからページ内移動。内容はHTMLに含める |

記事セクションを削り、その場所を制作の進め方とFAQに使う。LP内で「興味→理解→信頼→不安の解消→相談」が完結する構成とする。

### 3.2 各ブロックの編集量

| ブロック | 開始案 | 表示ルール |
| --- | --- | --- |
| Hero | 見出し2行程度、補足60〜100字程度 | 実文で調整し、固定高で文字を切らない |
| Technology | 3件、各説明80〜120字程度 | 見出しと要約は常時表示。3Dの選択だけで情報を切り替えない |
| Work | 2〜3件、画像各1点、要約各120〜180字程度 | 必要な補足だけ`details`で展開。主要な成果は閉じた状態でも見える |
| Process | 4工程、各説明40〜80字程度 | タイムラインの装飾はCSS。読み順は通常の縦順 |
| FAQ | 3〜4件、回答各80〜180字程度 | ネイティブの`details` / `summary`でJavaScriptなしでも開閉 |
| Contact | 案内、連絡先、メールで相談するボタン | メールアプリがない利用者も連絡先を選択・コピーできる |

文字数は原稿づくりの目安であり、文を切り捨てる制限ではない。初期コンテンツが実案件でない場合は「自主制作・コンセプト」と明示し、顧客実績や成果数値を捏造しない。

### 3.3 ナビゲーションとCTA

ヘッダーは「技術」「制作例」「進め方」と主CTA「相談する」に絞る。主CTAのページ内リンク先は全箇所で`#contact`に統一する。ヒーロー、制作例の後、ページ末尾に配置し、モバイルの常時追従CTAは初期には置かない。

通常の`<a href="#...">`を使い、URL共有、戻る・進む、キーボード操作を保つ。固定ヘッダー分の`scroll-margin-top`を確保し、アンカー先の見出しを隠さない。動きを抑える設定ではスムーズスクロールも無効化する。

モバイルメニューは非モーダルの`details`を基本とし、JavaScriptなしでもリンクを使えるようにする。補助スクリプトでリンク選択後の閉鎖とEscを扱い、フォーカスを失わせない。初期の`/#work`や`/#contact`への直アクセスでは、画面外のヒーロー3Dを読み込まない。

## 4. 3D・モーション体験仕様

### 4.1 Aether Coreの構成

基本形は12枚のフィン、3本のリング、中心核、少量の粒子。フィンの向き・間隔・リングの回転を変えるだけで、複数の状態を表現できる構成にする。

- 金属・曇りガラス風の質感は、軽量な環境反射とシェーダーで表現する。
- 屈折・多層透過・リアルタイム影を標準品質の前提にしない。
- 粒子は最大1,500個を出発点とし、InstancingまたはPointsでまとめて描画する。
- 現行モデルはオリジナルの手続き型ジオメトリーとする。形状・材質・照明の編集元を`scene.ts`で管理する。Blenderへの依存は持たない。
- 技術名・数値・リンクはCanvas内に焼き込まず、HTMLで表示する。

### 4.2 スクロールの演出譜

PCではHeroとTechnologyを一つのストーリー領域とし、**領域全体を約200svh、映像面を100svhのsticky**で開始する。短い演出の後に制作例へ進める長さにする。進行度は実際の領域高と表示高の差から計算し、文量・拡大表示で収まらない場合は通常フローへ切り替える。3Dのためだけに空のスクロール区間を追加しない。

下表の進行度はページ全体ではなく、この領域に対する値。数値は試作時の開始案であり、実文と実機で調整する。

| 進行度 | 視覚変化 | 情報・操作 | 実装方針 |
| --- | --- | --- | --- |
| 0〜20% | 組み上がったCoreが現れ、一度だけ光が走る | 主コピーとCTA。読み込みを待たずに表示 | 初期HTML＋静止画。最初の描画成功後に短くクロスフェード |
| 20〜55% | フィンが分離し、3つの技術領域が見える | 表現・体験・品質を説明 | transform中心。見出しはDOM。視覚位置と本文の順序を一致させる |
| 55〜80% | リングとフィンが整列し、接続線が生まれる | 技術を組み合わせて成果をつくることを説明 | カメラの過大な移動を避け、主にオブジェクトを変形する |
| 80〜100% | Coreが小さくまとまり、奥へ退く | 通常フローの制作例セクションへ接続 | 横スクロール化せず、次のセクションが自然に入る |

モバイル、狭い横画面、動きを抑える設定ではstickyによる長い演出を行わない。コピー→構造体の静止画または軽量3D→技術カードの縦積みとする。モバイルのヒーローが画面外に出た後はスクロール同期の対象とせず、技術カードだけで説明を完結する。制作例以降でヒーローを描画し続けない。

### 4.3 インタラクションの規則

| 操作 | 演出 | 制限・代替 |
| --- | --- | --- |
| PCで構造体にポインターを動かす | 最大約±4度の追従、弱い局所発光 | `pointer: fine`のときのみ。操作対象のクリック位置は移動させない |
| 技術カードを選択する | 対応する構造体の領域を強調 | ボタンで実装しキーボード対応。同じ説明を常にHTMLで読める |
| 制作例の補足を開く | 通常フロー内で説明を展開 | `details`の標準動作を優先。別ページ・モーダルは開かない |
| CTAを選択する | 相談領域へ移動、またはメールアプリを開く | 完了演出を捏造しない。メールを開くボタンは明確に表示 |
| FAQを開く | 回答をその場に表示 | 高さを固定しない。大きな展開アニメーションは不要 |

3D用の選択・停止・再試行ボタンは、スクリプトの初期化後に利用可能な状態だけを提示する。Q0やJavaScript無効時に反応しない操作部品を残さず、技術カードの見出しと説明は通常のHTMLとして維持する。

ネイティブスクロールを使い、スクロール速度やホイール入力を乗っ取らない。初回の演出は1秒程度で終え、操作がない間は静止する。可視領域に「動きを停止」ボタンを置き、スクロール連動・ポインター追従も停止できるようにする。停止切り替えで本文の位置やフォーカスを飛ばさない。

### 4.4 モーションの共通トークン

| 種別 | 時間の開始案 | 用途 |
| --- | --- | --- |
| instant | 100〜140ms | 押下、状態変化 |
| quick | 180〜240ms | ボタン、カード |
| standard | 320〜480ms | パネル、メニュー |
| cinematic | 700〜1,000ms | 初回のCore表示。操作をブロックしない |

UIはCSS、スクロールから目標進行度への変換はGSAP、3Dの補間・描画はThree.js側が担当する。同じプロパティを複数の仕組みから更新しない。GSAPの処理が止まった後も補間が収束するまでは描画し、収束したら描画ループを休止する。

## 5. 技術選定

### 5.1 推奨構成

| 領域 | 採用方針 | 理由・留意点 |
| --- | --- | --- |
| Web基盤 | Astro + TypeScript、静的出力 | 1ページのHTMLをビルド時に生成し、必要な場所だけ標準スクリプトで動かす |
| スタイル | CSS Custom Properties + セクションごとのクラス | 単ページの共通トークン・レイアウトを`global.css`に集約し、内容データと分離 |
| 3D | Three.jsを直接使用 | Canvasが1つのためReact・React Three Fiberを導入せず、初期JSと依存を減らす |
| 3D描画 | WebGLRendererによるWebGL2 | 見た目と動作範囲を優先。WebGPU実験は今回の範囲外 |
| モーション | CSS + GSAP / ScrollTrigger | 公式に無償提供を確認。独自ライセンスの制限・通知保持義務に従う |
| コンテンツ | `src/data/landing.ts`とローカル画像 | 型付きデータをビルド時に読み込む。CMS・外部コンテンツAPIなし |
| 画像 | AstroのImage / Picture | ローカル画像をビルド時に最適化し、表示寸法とレスポンシブ画像を出力 |
| テスト | Astroの型検査、Vitest、Playwright、axe-core | データ検証・品質判定・ページ内操作・視覚差分を確認 |
| 計測 | Web Vitalsと必要最小限の行動・エラー計測 | 利用サービスはP0で決定。無断で大きな解析SDKを加えない |
| 配信 | 商用利用可能な静的ホスティング＋CDN | `dist/`を配信。Vercelを使う場合はPro以上。常時稼働サーバー不要 |
| 問い合わせ | `mailto:`と表示されたメールアドレス | LP自体で個人情報を受信・保存しない。受信業務は通常のメールで行う |
| パッケージ管理 | pnpm、単一プロジェクト | 採用するAstro版に適合するNodeのサポート対象LTSを固定 |

Astro公式資料で、既定のビルド時静的生成、UIフレームワークなしの標準スクリプト、ローカル画像最適化を確認した（A01〜A03）。SSR用アダプター、サーバーAPI、CMS用SDKを導入しない。

### 5.2 比較と判断理由

| 選択肢 | 判断 |
| --- | --- |
| Next.js + React | 前案では複数ページ・CMSを理由に選定。今回はそれらが不要なため採用しない |
| Astro + React Three Fiber | 複雑なReactアプリとの統合は不要。単独シーンのためThree.jsを直接管理する |
| HTML / CSS / JSのみ | 表示は実現できるが、セクション分割、型、安全な画像処理、ビルド運用のためAstroを使う |
| WebGPU必須のトップページ | 不採用。APIの新しさのために閲覧可能性を失わない |
| 汎用の自由配置ページビルダー | 不採用。品質・性能・アクセシビリティを編集操作だけで壊せる構成を避ける |
| スクロール平滑化ライブラリー | 初期は不採用。ネイティブ操作と演出の同期で十分な品質を狙う |
| 常設の生成AIチャット | 初期は不採用。今回の価値と無関係な複雑さ、費用、誤情報リスクを増やさない |

バージョンは「latest」のまま運用せず、動作確認した組み合わせをロックファイルに固定した。Nodeは24系、今回の実行環境は24.0.1。運用ではサポート中の24系の更新パッチを適用して再確認する。Astro 7のプリレンダーがpnpmの外側から別版の`cookie`を解決しないよう、`vite.environments.prerender.resolve.noExternal`を設定している。

### 5.3 ライセンスと拡張の境界

GSAPの料金ページは全ユーザーへの無償提供を案内している。ただし独自ライセンスであり、Webflowと競合するノーコードのビジュアルアニメーション作成ツールへの利用などには制限がある。本LPの表示演出への利用とし、必要な著作権等の通知を保持する（S08）。

前回確認したThree.jsのWebGPURendererにはWebGL2バックエンドへのフォールバックがあるが、今回採用するWebGLRendererとは別の構成である（S07）。WebGPUや高品質専用モードのための分岐は初期には作らない。将来追加する場合も1ページ構成の目的と性能予算を改めて評価する。

## 6. アーキテクチャと境界

```text
制作担当 ──→ ローカルデータ・画像・表示コンポーネント
                    │
                    └─→ Gitでレビュー → Astroで静的ビルド
                                            │
                                     確認用配信 → 本番CDN

閲覧者 ──→ / の静的HTML
              ├─ 見出し、説明、制作例、FAQ、連絡先
              ├─ 軽量スクリプト: メニュー補助、3D開始判定
              └─ 条件成立時のみimport: Three.js、GSAP、3D資産

相談ボタン ──→ 同じページの #contact ──→ 利用者のメールアプリ
```

### 6.1 ディレクトリー案

以下は現在の実装構成。本文の更新と、表現・配信の変更を分けて管理する。

```text
src/
  pages/index.astro          唯一の公開コンテンツページ
  pages/robots.txt.ts        静的robots.txtを生成
  layouts/LandingLayout.astro
  components/
    Header.astro
    Hero.astro
    Technology.astro
    Work.astro
    Process.astro
    Faq.astro
    Contact.astro
    Footer.astro
  data/
    landing.ts              文言・制作例・FAQ・連絡先・メタ情報と型
    validate.ts             ビルド時の必須項目・リンク・ID検証
    publication.ts          環境変数から公開URL・連絡先・承認状態を取得
  assets/                   ポスター・制作例WebP、source/に図版のSVG原本
  scripts/
    page.ts                 軽量な操作補助・3D開始判定
  experience/
    index.ts                遅延importの入口、start / pause / dispose
    scene.ts                Core、照明、カメラ、資産
    motion.ts               スクロール・ポインターから目標値への変換
```

Astroのビルド側でローカルデータを読み込み、本文と画像をHTMLへ出力する。`landing.ts`全体をクライアントへシリアライズしない。3Dへ渡すのは必要な領域IDと小さな設定だけにする。

`page.ts`はThree.jsやGSAPを静的importしない。条件成立後だけ`experience/index.ts`を動的importし、その配下に重い依存を閉じ込める。3D資産の先読みも開始条件の後に行う。ビルド時の自動バンドル処理だけで取得順を保証せず、本番出力のネットワークで検証する（A02）。

### 6.2 描画・状態管理

- 本文とポスターを静的HTMLで最初に配信し、Canvas初期化をLCPの前提にしない。
- Canvasは1つ。制作例カードに追加のCanvasを作らない。
- スクロール進行度・ポインターは小さな状態オブジェクトで管理し、毎フレームDOMを生成し直さない。
- DOMサイズはResizeObserver等で必要時だけ取得し、毎フレームのレイアウト読み取りを避ける。
- ループは表示領域内で変化がある間だけ動かす。非表示タブ、領域外、停止状態では休止する。
- 描画スケジューラーの所有者を1つにし、GSAPの更新は目標値の変更と描画要求だけを行う。補間収束後は連続描画を止める。
- 破棄時にイベント・observer・タイムライン・描画資産を解放する。戻る操作でのbfcache復帰では重複初期化せず、停止から正しく復帰する。
- 停止中・読み込み中の再クリックでCanvasやイベントが増えないようにする。

AstroのClientRouterやSPA化は行わない。ページ内移動にルーターは不要であり、更新時には静的ファイルを再配信するだけとする。

### 6.3 体験のライフサイクル

`poster → loading → interactive`を基本とし、`paused`と`static-error`を明示的な状態として扱う。

初回は必ずポスターを表示し、文字やCTAに「準備完了待ち」の透明化をかけない。ポスターのデコード、初期レイアウト、URLのアンカー位置への移動を終え、可視領域と設定条件が合った場合にのみ3Dを取得する。初期画像やフォントより高い優先度で先読みしない。アイドル時に開始し、利用できない環境では初期表示後の別タスクとして開始する。待機後のimport直前と描画開始直前に条件を再確認する。読み込みに時間がかかってもポスターを維持し、操作を塞ぐローダーを表示しない。

Canvas生成失敗、モデル不正、WebGLコンテキスト喪失時は静止画へ戻し、「軽量表示に切り替えました」と通知する。原因を機密情報なしでログに記録し、明示的な「3Dを再試行」操作を提供する。自動再試行の無限ループは作らない。停止・非表示・OS設定変更が読み込み中に発生した場合も、完了後に勝手に再生しない。

実装ではコンテキスト喪失等はシーンを解放して再初期化する。コード取得自体の失敗はブラウザーのモジュールキャッシュに残るため、「ページを再読み込みして再試行」と明示し、利用者の操作時だけページを再読み込みする。自動リロードは行わない。

## 7. 品質の段階化と性能予算

### 7.1 品質レベル

| レベル | 適用条件・方針 | 描画仕様の開始値 |
| --- | --- | --- |
| Q0: 静止画 | 動きを抑える設定、手動の軽量表示、Save-Dataが取得でき有効、初期化失敗 | AVIF/WebP等のポスター＋全HTML本文。開始時にQ0なら3Dバンドルを要求せず、読み込み後の移行では描画を停止 |
| Q1: 標準 | 抑制条件がなく、ヒーローが可視、WebGL2初期化に成功 | DPR上限1.5、描画バッファー200万画素以下、80k三角形以下、50 draw calls以下、粒子1,500以下 |
| Q1低負荷 | 継続的なフレーム遅延を検出 | DPR上限1.0、描画バッファー100万画素以下、粒子500以下。モデルは共有し、重いポスト処理なし |

画面幅を端末性能の判定に使わない。幅はレイアウトの切り替えだけに使い、品質は初期化結果と実測で調整する。`deviceMemory`やネットワーク情報は存在しない環境があるため必須にしない。端末情報を組み合わせて識別用の指紋を作らない。

動きを抑えるOS設定は最優先とし、有効な間は自動開始も再試行による再生も行わない。手動停止は現在の閲覧中に保持する。初期版に高品質選択UI・Q2・設定の永続化は作らず、標準表示から必要に応じて軽くする。

### 7.2 実測による品質調整

可視かつ連続描画が必要な操作中に、1秒のウォームアップ後、2秒窓を3回観測する。各窓のフレーム間隔p95が25msを超え続ける場合はQ1低負荷へ降格する。変更後に新しい窓を取り、それでもp95が40msを超え続ける場合はQ0へ移行して通知・記録する。

意図的に休止している時間を低fpsとして数えない。非表示タブ・領域外・操作終了をまたぐ窓は破棄する。降格後は同じ閲覧中に自動昇格させない。フレーム間隔はGPU処理時間そのものではないため、原因調査にはCPU/GPUのプロファイルを併用する。

### 7.3 転送・描画予算

KiB/MiBは1,024進数。コールドキャッシュで圧縮後レスポンス本文の転送量を集計し、遅延資産は「追加分」として数える。PC 1,440×900、モバイル390×844の標準サイズで測定し、他サイズの表示確認も行う。

| 指標 | 目標・上限 | 確認方法 |
| --- | --- | --- |
| 初期JS | 35KiB以下 | メニュー補助・開始判定・初期計測を含む。Three.js・GSAPは含めず別バンドル |
| 初期表示の合計転送 | 500KiB以下 | 初期HTML、CSS、JS、フォント、ポスター、初期画像を含む |
| ヒーローポスター | PC 160KiB以下、モバイル100KiB以下 | 実際に選択されるレスポンシブ画像のサイズ |
| 初期フォント | 合計70KiB以下 | 英数字中心に自前配信。日本語はシステムフォントを基本とする |
| 遅延3Dコード | 追加450KiB以下 | Three.js、GSAP、補助コード、使用するデコーダーを含む |
| 遅延3D資産全体 | 追加1.2MiB以下 | コード、モデル、テクスチャ、環境マップを合算 |
| LP全体の転送 | 3MiB以下 | ページ末尾までスクロールし、制作例・FAQの補足をすべて開いた状態。3Dも含む |
| アクティブ描画 | 基準PCで60fps目標、代表モバイルで30fps以上を目安 | ヒーローの可視領域内で10秒間操作。p95フレーム間隔はPC 20ms以下、モバイル33.3ms以下 |
| 推定GPU資産使用量 | Q1で64MiB以下 | テクスチャの展開後サイズ、ミップ、ジオメトリー、描画バッファーから推計 |
| 領域外・非表示タブ | 継続的な描画ループを停止 | Performance記録で不要な連続フレームがないことを確認 |

初期表示500KiBと遅延3D 1.2MiBを合わせて約1.7MiB以内、残りを制作例画像などに配分する。初期画像のブラウザー先読みも実際に取得された分を計上する。画像・解析を単に遅延させて全体予算から除外しない。GPU資産量は推計と実機の安定性を併記する。

初期区間は3D無効の計測条件で初回表示から5秒間を測り、3D有効の通常経路でも非3D要求を分類して同じ上限を確認する。LCP等の速度判定は3Dを無効にした場合だけでなく、標準の有効経路でも実行する。

### 7.4 Core Web Vitalsと測定条件

公開後はモバイル・PCを分けた実利用データのp75で、LCP 2.5秒以下、INP 200ms以下、CLS 0.1以下を目標とする。公開前のラボ測定を実利用データと同一視しない。データ数が不足する場合は達成判定を保留する。

公開前は本番相当ビルド・コールドキャッシュ・下り10Mbps／上り1Mbps／遅延150msを基準条件とする。唯一のLPを、標準3D・Q0の各条件と各基準端末で5回測定する。LCP中央値2.5秒以下、CLSは全試行0.1以下を公開条件とし、LCPが一度でも4秒を超える場合は原因を調査する。

メニュー、3D停止、CTA、FAQの操作から次の描画まで200ms以下を目標とする。これは制御された操作試験であり、実利用のINP達成値とは区別する。LighthouseのTBTもINPの代替値として報告しない。

基準実機の候補は、Apple Silicon搭載ノート、内蔵GPUのWindowsノート、iPhone 13級、Pixel 6a級、4GBメモリーの廉価Android端末。実際の機種、OS、ブラウザー版はP0で記録し、同じ条件で比較する。ブラウザーは公開時点のChrome・Edge・Firefox・Safariの現行と一つ前の主要版、iOS SafariとAndroid Chromeを対象候補とし、提供者のサポート状況に合わせて確定する。

### 7.5 資産最適化の手順

**現行は手続き型モデルのため、以下のglTF・テクスチャ圧縮工程は不要。** Three.jsとGSAPを含む遅延コードだけを配信し、環境反射も端末内で生成する。今後外部モデルを導入する場合の手順として以下を残す。実モデルのポスターは`pnpm poster`で再生成する。

1. Blenderの編集用データから、不要な面・マテリアル・ノードを除去する。
2. glTF/GLBを基本にし、Meshopt等の圧縮効果とデコーダー費用を比較する。
3. テクスチャは適切な解像度とKTX2/Basis等を候補にし、透過・色空間・端末互換性を確認する。
4. 圧縮後モデルから、実際の初期カメラと同じポスターを生成する。
5. サイズ、三角形数、draw calls、ライセンス、代替画像を資産単位で記録する。

高品質化のために毎回フルスクリーンのポスト処理を追加しない。優先順位は、構図→光→マテリアル→動き→追加エフェクトとする。

## 8. CMSなしでのコンテンツ管理・更新

### 8.1 ローカルデータの構成

`src/data/landing.ts`に表示内容を集約し、`LandingContent`型と`satisfies`等で構造を確認する。表示コンポーネントへ直接原稿を埋め込まない。

| データ | 主な項目 | 制約 |
| --- | --- | --- |
| meta | title、description。公開URLは`publication.ts`から取得 | 本番URLと共有用画像を検証 |
| hero | 見出し、補足文、CTAラベル、ポスター | 主CTAは`#contact`、副CTAは`#work` |
| technology | 領域ID、名称、価値の説明 | 領域IDは固定の3種類。3Dとの対応を検証 |
| work | ID、名称、画像、alt、種別、課題、担当、成果、補足 | 2〜3件を基本。種別は実案件とコンセプトを区別 |
| process | 見出し、工程、運営者紹介 | 承認された提供体制だけを記載 |
| faq | 質問、回答 | IDの一意性と空回答を検証 |
| contact | 案内、件名。受信先は`CONTACT_EMAIL`から取得 | ダミー連絡先のまま本番用ビルドしない |
| privacy | 方針、運営者情報、更新日 | 実際のメール対応・計測方針と一致させる |

画像は`src/assets/`からimportしてAstroで処理する。現行の`public/`にはOGとfaviconのみを置く。将来ここにモデル・テクスチャを置く場合はそのまま配信されるため、別途最適化する（A03）。本文はテキストや固定の段落構造とし、任意HTMLを差し込まない。

必須項目、存在しない画像、重複ID、不正なリンク先はビルド時に明示的なエラーとする。未設定の連絡先はプレビューだけで許可し、本番用ビルドではエラーとする。`.env.example`と`walkthrough.md`に公開設定を記載した。型検査では判定できない内容を`validate.ts`で確認し、失敗したビルドを公開しない。

### 8.2 更新範囲の分離

**通常の内容変更:** `landing.ts`と画像のみを編集。見出し、制作例の差し替え、FAQ、連絡先、SEO情報を更新できる。

**表現の変更:** コンポーネント、共通トークン、3Dのシェーダー・動き・品質判定を編集。視覚差分と性能を再確認する。

将来のデータ取得元変更に備え、表示コンポーネントはデータをpropsで受け取る。ただし現時点でCMSアダプター、汎用ページビルダー、プラグイン構造は作らない。

### 8.3 更新・公開フロー

1. 制作担当が原稿・画像を変更し、型検査と内容検証を行う。
2. ローカル表示またはブランチの確認用配信で、PC・モバイル・Q0を確認する。
3. レビュー担当が内容・権利・連絡先を承認する。未公開情報を含む確認用配信はアクセス制限し、`noindex`だけに頼らない。
4. 承認済みの変更を静的ビルドし、成功した成果物だけを本番へ切り替える。
5. 本番URLで本文・画像・アンカー・連絡先を確認する。失敗時は直前の成果物へ戻す。

HTMLは更新を再確認できるキャッシュ方針とし、内容ハッシュ付き資産は長期キャッシュする。HTMLと資産を一体で切り替え、旧ページが参照する資産を即時削除しない。ブラウザーに古いコンテンツを固定するService Workerは導入しない。

公開反映はレビュー・ビルド・配信に依存する。前案のCMS公開後60秒以内という条件は撤回し、配信後の実URL確認で完了とする。権利取り下げ時は該当内容の再配信に加え、元画像・確認用配信・CDNの公開停止も確認する。取得済みファイルの遠隔回収は保証しない。

### 8.4 更新性の受け入れ条件

- 支給済み素材による制作例1件の差し替えを、`landing.ts`と画像の変更だけで行える。
- 制作担当が上記差し替えからローカル確認まで15分以内で実施できる。原稿作成・承認・CI待ち時間は含めない。
- 文言変更のためにHTML構造・CSS・3Dコードを編集しない。
- 長い日本語、縦長画像、FAQの長文でも内容が切れず、空の任意項目で表示が壊れない。
- ビルド失敗は本番へ反映されず、直前版への復旧手順を実行できる。

管理画面によるノーコード編集ではない。Git・開発環境を扱える制作担当が更新する運用を前提とする。

## 9. アクセシビリティ・SEO・問い合わせ

### 9.1 アクセシビリティ

目標はWCAG 2.2 AA。自動検査だけで適合を断定せず、キーボードと支援技術で主要導線を確認する。

W3Cの解説で、2.5.8の最小ターゲットは例外条件付き24×24 CSS px、2.2.2では他の内容と並行する自動的な動きが5秒を超える場合に停止等の手段が必要であることを確認した。本設計の44×44pxと、OS設定に加えた明示的な停止ボタンは、使いやすさを優先したプロジェクト方針。これらだけでAAの全要件を満たしたとは判断しない（S14・S16）。

- Canvasは装飾として扱い、スクリーンリーダーには同等の説明をHTMLで提供する。3Dだけに重要情報を置かない。
- `prefers-reduced-motion: reduce`では3Dの自動開始、パララックス、スクロール同期を無効化する。
- ページ読み込み時に本文を透明化してアニメーション待ちにしない。
- 「動きを停止」「軽量表示」をキーボードから操作できる位置に配置する。
- 本文へスキップ、適切なランドマーク、見出し階層、常時見えるフォーカスリングを用意する。
- モバイルメニューとFAQは標準の開閉操作を保つ。メニューを非モーダルとし、不要なフォーカストラップや背景の操作制限を付けない。
- タッチ対象は原則44×44 CSS px以上。固定ヘッダーはアンカー移動先やフォーカスを隠さない。
- 320 CSS px幅、200%文字拡大、400%ズームで主要情報と操作を維持する。必要なら演出領域を通常フローにする。
- 一秒に三回を超える点滅、急激な全画面ズーム、強いカメラ回転を避ける。
- 自動再生の実績動画は採用しない。ユーザー操作で開始し、必要な字幕・説明を用意する。

### 9.2 SEO・共有

タイトル、説明、canonical、OG画像、robots、正しいHTTPステータスを用意する。canonicalはルートURLに統一し、`#work`等を別ページとして登録しない。サイトマップを作る場合もルートの1URLのみ。画像・robots・サイトマップは配信資産であり、追加のLPページではない。

本文、制作例、FAQの回答、連絡先は初期HTMLに含める。構造化データは事実に沿うOrganization・WebSite等に限定し、架空の評価を入れない。記事用Articleや階層のないBreadcrumbListは作らない。FAQを置くだけで検索結果の特別表示を保証するものではない。

OG画像は1枚の静的画像とし、Canvasの実行を必要としない。存在しないURLは配信基盤で404を返し、何でもLPへ200で転送するSPA設定にしない。確認用配信の検索除外と、本番の検索許可を分ける。

### 9.3 相談導線

`#contact`に「メールで相談する」ボタンと、選択・コピーできるメールアドレスを置く。`mailto:`の件名だけを適切にエンコードし、本文に利用者の情報を自動埋め込みしない。公開前に実際の受信先、運営者、対応可能な内容を確定する。

これはメールアプリを開くリンクであり、LPでの送信処理ではない。「送信しました」「受付完了」などの表示や完了ページは作らない。メールアプリが未設定でも、表示された連絡先から手動で送れるようにする。JavaScriptや3Dが無効でも利用できる。

利用者情報はLPのフォームでは収集しないが、受信メールや配信基盤のログにも取り扱いが必要。`#privacy`に実際の運用に合った方針を記載する。架空の返信時間やサポート条件は約束しない。

将来フォームをLP内に追加する場合は、送信先、入力検証、迷惑送信対策、同意、保存先、送信結果、JavaScript無効時の代替を別途設計する。現段階で見た目だけの送信フォームを置かない。

## 10. 安全性・可観測性・継続運用

### 10.1 公開前の基本対策

HTTPS、依存関係検査、CSP、公開データの検証、確認用配信のアクセス制限を実施する。CSPはReport-Onlyで必要な通信・Worker・デコーダーを把握し、本番では検証済みの制約を有効化する。ビルドでinline scriptが生成される場合もハッシュ等で扱い、安易に`unsafe-eval`を許可しない。

CMS・メール送信用のAPIキーは不要。配信基盤の認証情報はビルド・配信環境に限定し、公開データや生成HTMLへ入れない。メール本文・利用者のアドレスは解析やエラー監視へ送らず、セッション録画も初期には導入しない。

### 10.2 計測設計

以下は本公開時に運用先を決めて導入する設計。現行実装では外部計測を行わず、状態通知・ブラウザーのコンソールとテストレポートに限定する。

| 計測 | 内容 | 注意点 |
| --- | --- | --- |
| Web Vitals | LCP、INP、CLS、3Dの表示条件 | 個人情報を含むURLパラメーターを除去 |
| 体験状態 | 3D初期化成功・失敗、Q0への移行理由 | GPUの詳細識別情報は不要 |
| 主要行動 | 相談CTA、相談領域への到達、メールリンクのクリック | 送信完了率として集計しない |
| 運用 | ビルド・配信失敗、主要資産の取得失敗 | 対応担当・通知先・復旧方法を決める |

相談領域への到達は「50%以上が1秒以上表示」等の定義をP0で固定し、同一閲覧中の重複を除く。スクロールの毎フレーム送信は行わない。解析の同意要否・データ移転はサービスと公開対象地域に応じて確認し、同意拒否でも本文・3D・連絡先を使えるようにする。

### 10.3 保守

- 月次で依存関係と脆弱性を点検し、緊急修正は別経路で対応する。更新PRごとに型・主要操作・視覚差分を確認する。
- 内容、表示コンポーネント、3Dを分離し、変更範囲に応じた確認を行う。
- モデル・テクスチャは内容ハッシュまたはバージョン付きURLで配信し、旧デプロイが参照する資産を即時削除しない。
- Git履歴、編集元3Dデータ、画像原本、公開済み成果物を保管し、復元を確認する。
- 3Dを無効化するビルド設定を用意する。障害時は静止画版を再配信し、設定が即時反映される動的スイッチとは扱わない。
- ソースコード、ドメイン、配信先、計測、メール窓口の管理主体を同一の組織所有へ揃える。

費用は静的ホスティング、ドメイン、資産転送、必要な計測、素材・フォント、制作工数が中心。CMSの席数料金、データベース、メール送信API、更新用キューは不要とする。通常のメール受信環境の費用は別途確認する。

配信先は商用利用条件と予算で確定する。Vercelを選ぶ場合、Hobbyは非商用の個人利用限定のため対象外。前回確認したProの基本料金表示は月額20米ドルで、利用量・追加席・税等を含む総額ではない（S17）。静的LPであること自体は無料プランの商用利用許可を意味しない。

### 12.2 公開ゲート

1. **価値:** 初回表示で提供価値とCTAが分かり、同じページだけで制作例・進め方・相談方法を理解できる。代表的な閲覧者5名を目安に観察する。
2. **内容:** 実案件とコンセプトを区別し、素材の権利・連絡先・個人情報の方針を承認する。
3. **機能:** 1つの公開HTMLにすべてのセクションがあり、全アンカー・開閉・相談リンクが動作する。追加ページへの必須導線を残さない。
4. **包摂性:** Q0、JavaScript無効時、キーボード、動きを抑える設定で本文・FAQ・連絡先を利用できる。
5. **性能:** 初期JS 35KiB以下、初期転送500KiB以下、遅延3D追加1.2MiB以下、LP全体3MiB以下と、第7章の速度・描画条件を満たす。
6. **更新:** 制作担当がデータと画像だけで制作例を差し替え、ローカル確認とレビュー・再配信を行える。
7. **運用:** 本番の受信窓口、ビルド失敗通知、静止画版の再配信、取り下げ、ロールバックを確認する。

### 12.3 公開後の改善

公開直後は資産の取得エラーと相談導線を確認し、その後に実利用データで性能とCTAを見直す。Web Vitalsの集計期間・母数を併記し、少ないサンプルから達成を宣言しない。初期はA/Bテスト用サービスを常設せず、原稿や配置を静的更新して改善する。
